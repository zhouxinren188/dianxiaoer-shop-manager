# 云仓助手异常订单流程接手说明

更新时间：2026-09-02

当前专项分支：`codex/cloud-warehouse-assistant`

本轮起点提交：`f825233da687d633c9ee7325a833f2642affc5cb`

## 1. 当前结论

店小二不再充当云仓助手执行器的中央中转服务。云仓助手是独立第三方服务，负责设备在线状态、任务分发、实际异常查询/处理及结果返回；店小二只负责：

1. 按主账号体系保存用户绑定的 `machine_code`；
2. 从关联销售订单可靠取得订单号和年份；
3. 由店小二业务服务端查询绑定设备是否在线并提交固定白名单命令；
4. 保存第三方任务及脱敏回执，向页面展示结果；
5. 在页面内完成店小二自己的自动备注、状态展示、手工兜底等交互。

当前已启用：

- `exception.order.check`
- `exception.order.resolve`
- `warehouse.order.check`（全量查询，不传订单号；详见
  [云仓订单全量查询与待打印核验契约](./cloud-warehouse-order-query-contract.md)）

以下命令继续禁用，不得提前接入：

- `warehouse.order.print`
- `warehouse.order.outbound`

旧文档中的登记、Token、心跳、能力上报、任务领取、租约、执行器订单映射和结果回传属于历史控制面方案，不得继续部署或扩展。

## 2. 问题与需求背景

采购订单的“云仓打单发货”弹窗需要帮助用户完成以下异常订单流程：

1. 第一次进入且从未查询过时自动查询一次异常；
2. 查询到异常后展示全部脱敏异常明细；
3. 用户点击“处理异常”并确认；
4. 店小二先尝试把采购编号自动备注到关联京东销售订单；
5. 不论自动备注成功或失败，都继续向云仓助手提交异常处理命令；
6. 收到明确成功回执后提示处理中，并自动重新查询一次异常状态；
7. 页面记录查询异常、自动备注、处理异常三个阶段的处理日志；
8. 没有异常时不展示空的异常结果区域；
9. 原有“我已转发”按钮继续保留，供没有云仓助手或已在线下完成发货的用户手工标记。

本轮联调还暴露了两个用户可见问题：

- 云仓助手的错误体为对象时被直接转成字符串，页面显示 `[object Object]`；
- 处理命令已经成功，但随后刷新配置失败时，共用的异常捕获会误报“发送异常处理指令失败”。

## 3. 原因分析

### 3.1 旧架构与当前架构混杂

项目早期实现过店小二中央执行器控制面，相关历史表和文档仍然存在。最终架构改成店小二业务服务端直接调用云仓助手第三方 API，因此必须明确区分历史代码/表与当前实际调用链，避免误部署旧端点。

### 3.2 页面只有最终状态，没有可追溯过程

异常查询和处理结果原本只反映在当前状态上，自动备注又发生在 Electron 本机，用户无法清楚分辨“查询、备注、处理”分别是否成功。因此需要组合第三方任务记录与店小二本机动作日志。

### 3.3 处理后的复查可能被旧处理回执覆盖

异常处理成功后会产生 `waiting_arrival` 回执；自动复查如果仍查询到异常，最新查询结果必须优先。旧状态归并逻辑无条件让处理回执覆盖查询结果，可能把仍有异常的订单显示成正常。

### 3.4 错误阶段没有隔离

前端过去把“提交命令、读取最新配置、启动复查”放在一个 `try/catch` 中。只要后续读取失败，就会被错误包装成发送失败。第三方客户端还直接对 `response.error` 调用字符串转换，遇到对象便产生 `[object Object]`。

## 4. 当前有效的数据和接口契约

### 4.1 主账号体系机器码绑定

- 绑定单位是店小二主账号体系，不是单个登录账号；
- 主账号及其已授权子账号共享同一个绑定机器码；
- 前端不能在单次任务中传入或自由选择机器码；
- 店小二服务端必须按实际登录人的主账号归属自动取得机器码；
- 同一机器码不能被无关主账号体系占用；
- 绑定、解绑和换绑只允许主账号或具备管理权限的管理员操作。

机器码格式：

```text
^YC-[23456789ABCDEFGHJKLMNPQRSTUVWXYZ]{4}-[23456789ABCDEFGHJKLMNPQRSTUVWXYZ]{4}$
```

### 4.2 订单定位

异常接口查询参数必须来自关联销售订单：

```text
order_no   = sales_orders.order_id
order_year = YEAR(sales_orders.order_time)
```

禁止使用采购单 `created_at`、当前年份、订单号格式或人工猜测年份。采购编号只用于京东自动备注和店小二审计，不作为异常接口查询号。

### 4.3 云仓助手第三方接口

基础地址：

```text
https://150.158.54.108:3443/api/cloud-warehouse/v1
```

店小二服务端只调用：

```text
GET  /machines/:machineCode/status
POST /commands
GET  /commands/:requestId
```

命令请求固定字段：

```json
{
  "request_id": "每次新操作唯一；同一次网络重试保持不变",
  "machine_code": "主账号体系绑定机器码",
  "command": "exception.order.check",
  "order_no": "sales_orders.order_id",
  "order_year": 2026
}
```

当前协议不使用 API Key，不固定叶证书指纹，必须保留 Node.js 系统标准 CA 信任链和 IP SAN 校验；禁止关闭证书校验。

HTTP `200` 表示已有最终结果，`202` 表示任务尚未完成。轮询必须继续使用原 `request_id`，不能生成新编号重复下发。

### 4.4 异常处理快照

店小二提交 `exception.order.resolve` 时仍只发送上述固定字段，不传异常 ID 或快照编号。云仓助手服务器按相同机器码、订单号和年份自动关联最近一次有效查询快照。店小二必须先有成功且确认存在异常的查询结果，才允许提交处理命令。

## 5. 本轮修改方案与关键行为

### 5.1 首次自动查询

仅当以下条件全部成立时自动查询一次：

- 当前为第三方服务模式；
- 主账号体系已绑定机器码；
- 关联销售订单号和年份有效；
- 当前订单从未产生工作流、异常查询或异常处理记录。

已有成功、失败、不确定或进行中的历史记录均不会因重复打开弹窗而再次自动下发。

### 5.2 处理异常前自动备注

用户确认处理异常后：

1. 读取当前采购编号；
2. 通过既有 Electron 京东商家备注能力，把采购编号提交到关联京东销售订单；
3. 京东备注成功时尽力同步本地销售订单备注；
4. 持久化一条自动备注处理日志；
5. 备注失败时短暂提醒用户，但仍继续提交异常处理命令。

自动备注结果只是过程审计，不参与云仓助手业务成功判定。

### 5.3 动态处理按钮

用户确认后，按钮立即显示加载动画和“处理中…”。该状态覆盖本地自动备注、异常处理提交及云仓助手远程执行阶段。按钮禁用用于防止用户重复写入，不代表业务失败。

### 5.4 处理成功后自动复查

只有异常处理满足以下条件才自动复查：

- 传输状态为 `completed`；
- 云仓助手业务状态为 `succeeded`；
- 尚不存在时间晚于本次处理回执的异常查询结果。

复查使用新的 `request_id`。如果最新复查仍有异常，则最新查询结果优先，页面继续显示异常；如果确认无异常，则显示“暂无异常”。不会自动再次执行异常处理。

### 5.5 处理日志和异常结果

“接口对话记录”更名为“处理日志”。日志来源：

- 查询异常、处理异常：`cloud_external_commands`；
- 自动备注：`cloud_order_process_logs`。

页面合并展示查询、自动备注、处理异常的状态、脱敏消息和时间。异常明细区域只在最新查询明确成功且异常数量大于零时展示；无异常时整个明细区域隐藏。

### 5.6 错误与刷新降级

- 第三方返回对象形式错误时，只提取已知文本字段，绝不再显示 `[object Object]`；
- 命令提交、最终业务回执、配置刷新分别提示；
- 已确认成功的处理不会被后续刷新错误改写成发送失败；
- 活跃任务刷新第三方状态失败时，店小二配置接口仍返回已有任务和回执，并附带 `workflow.refreshFailure`；
- 页面显示“状态查询失败”，继续保留已有记录，轮询可在后续请求恢复；但远端明确返回 404/410 或“指令不存在”时，必须把该指令记为失败终态并释放“处理中”，允许用户再次操作；
- 不因状态不确定而自动重复写操作。

## 7. 数据库迁移与部署顺序

新增表：

```text
cloud_order_process_logs
```

关键字段：主账号体系、采购单、实际操作人、动作、状态、脱敏消息、发生时间。

推荐部署顺序：

1. 先合并并部署店小二业务服务端；
2. 执行/复验 `initDB`，确认新表创建成功；
3. 验证现有 `cloud_external_commands` 数据不受影响；
4. 再发布 renderer 热更新；
5. 用测试账号验证机器码在线查询；
6. 先测 `exception.order.check`，再用指定测试订单人工确认后测试 `exception.order.resolve`。

本轮没有主进程代码改动，renderer 可采用热更新；但服务端必须先部署，否则自动备注日志接口会返回 404。页面已有当前会话内的本地日志降级，不会因此阻断异常处理，但日志不能跨会话持久化。

## 8. 风险点

1. **第三方公开接口当前无独立 API Key**：机器码只是路由标识，不是凭据。必须持续评估云仓助手服务器的认证、限流、重放防护和机器码泄露风险，店小二不得把该接口暴露给 renderer 直接调用。
2. **第三方可用性**：设备状态、命令提交和结果轮询依赖云仓助手服务器。读取失败必须显示“状态查询失败”，不能直接等同于设备离线，也不能覆盖已经确认的写操作结果。
3. **自动备注为客户端上报日志**：京东操作发生在 Electron 本机，服务端保存的是客户端报告的过程结果，不能把该日志当成云仓业务状态的权威依据。
4. **订单年份可靠性**：`sales_orders.order_time` 缺失或无效时必须停止，不得回退到采购单时间或当前年份。
5. **快照时效**：异常处理依赖云仓助手最近一次查询快照，用户确认和处理应在服务端规定时间内完成；过期或异常集合变化应重新查询。
6. **写操作不可自动重试**：网络超时、结果不确定或状态矛盾时只允许查询原 `request_id`，不能生成新请求自动重发 `exception.order.resolve`。
7. **历史控制面遗留**：数据库中可能仍有 `cloud_executor_*` 等旧表。它们暂不删除，但没有发布依据，不得误认为仍需心跳或任务领取。
8. **日志长度和脱敏**：处理日志消息最多500字符，并脱敏 Authorization、API Key、Cookie、Token、密码、Secret 和 Credential 等常见凭据形式；新增错误来源时需要补充脱敏规则。

## 10. 后续维护注意事项

- 任何新业务命令必须单独确认接口、能力开关、请求字段、成功状态和写后复验，不得从现有异常命令推断；
- 不要把机器码作为密码，也不要允许前端为单次命令指定其他机器码；
- 不要把云仓助手 Cookie、账号、Token 或平台凭据上传店小二；
- 修改状态归并时必须同时覆盖“处理后复查仍异常”和“处理后复查无异常”两种顺序；
- 修改轮询时必须复用原 `request_id`，并区分只读轮询与写命令重发；
- 页面提示必须区分：提交失败、业务失败、状态刷新失败、设备离线和结果不确定；
- 新增本机动作时写入 `cloud_order_process_logs`，第三方命令仍以 `cloud_external_commands` 为唯一权威记录，避免重复存储回执；
- 部署前先检查主线是否有并行修改，发生冲突或取舍不明确时停止并报告；
- 专项本地开发保持 renderer `5175`、本地服务 `3004`、数据目录 `.dev-user-data-cloud-warehouse-assistant`，不要改回其他支线端口；
- 最终合并、服务器部署和客户端发布由主线窗口审查执行，专项窗口不得自行合并主线或发布。
