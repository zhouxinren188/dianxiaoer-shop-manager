## 2. 问题与需求背景

项目已经实现淘宝按商品主图搜索同款、打开同款商品页、展示销售商品信息、选择/取消货源、记录 SKU 和价格等能力。长期问题主要集中在搜索会话：

1. 同一个淘宝账号在其他工具中可以正常搜同款，但本项目偶发或持续返回 `RGV587_ERROR::SM::哎哟喂,被挤爆啦,请稍后重试!`。
2. 搜索窗口若复用采购账号 partition，会与商品页、自动选 SKU、改地址、下单等流程互相影响，曾出现淘宝账号掉线、优惠价圆点不展示等风险。
3. 仅把采购账号 Cookie 复制到另一个搜索 partition 也不可靠，因为淘宝登录环境不仅包含 Cookie，还包含 localStorage、IndexedDB、Service Worker、设备/页面上下文和动态安全参数。
4. 采购账号可能有多个，搜索会话跟随采购账号切换会反复冷启动，无法达到其他工具“首次稍慢、后续立即复用”的效果。
5. 用户提出使用一个完全独立的淘宝搜索账号：首次点击弹出登录，登录后隐藏窗口，后续所有商品固定复用该窗口和完整浏览器环境。

## 3. 原因分析

### 已确认的问题

- 早期方案把搜索和采购放在同一个 `persist:purchase-{accountId}` 中，搜索页面与采购流程共同读写登录 Cookie、MTOP Token 和站点状态，隔离边界不足。
- 后续失败方案使用 `persist:dianxiaoer-tb-search-v2-{accountId}`，但会从当前采购分区或服务器复制 Cookie，并在缺少登录 Cookie 时清理搜索存储。日志证明即使复制了 59/105 条 Cookie，仍可能立即被淘宝拦截或删除 `unb`、`cookie17`。
- 说明“复制 Cookie”不能重建淘宝认可的完整登录环境，而且清理/恢复动作增加身份突变与风控概率。
- `4bc7c54` 已增加关键身份 Cookie 指纹、会话代际、请求前身份复核、全 frame 登录/验证识别等防护。这些防护应保留，但只监控专用搜索会话。

### 最新日志结论（2026-08-12 02:27—02:28）

- `02:27:44` 打开专用账号登录窗口。
- `02:27:45` 日志写了“开始搜同款”，但随后命中 `login_cookie_missing_before_search` 并直接返回，没有准备图片、没有发送 MTOP 请求。该日志名称/位置有误导性。
- `02:28:12` 登录身份 Cookie 开始写入。
- `02:28:18` 登录环境判定稳定，窗口自动隐藏。
- `02:28:21` 用户再次点击搜索。
- `02:28:22` 才第一次真正发送 MTOP 请求。
- 真正请求是在登录完成后发出的，不是未登录时偷跑；但请求环境诊断显示 `bixi.coherent=false`，随后淘宝返回 `RGV587`。

重要纠偏：蚂蚁工具箱 2026-08-11 的已知成功样本同样没有 `bx-ua`、`bx-umidtoken`、`bx_et`，仍在第一次 MTOP 请求中成功返回 60 条结果。因此 `bixi.coherent=false` 只是本次日志现象，不能认定为失败原因，更不能通过伪造、写死或跨会话复制 Bixi 来修复。

当前未解决重点不是“登录前提前发请求”，也不能简化成“缺少 Bixi”，而是专用会话登录后仍需逐项对照成功环境的承载页生命周期、资源加载、Token/导航稳定、页面内 XHR 和真实网络上下文。禁止通过盲目刷新、反复重试、复制 Cookie 来掩盖问题。

2026-08-12 04:04 已完成一次 `webSecurity=false` 单变量验证：第一次请求仍在 125ms 返回相同的无验证 URL `RGV587`；真实出站请求的 `Origin` 从 `webSecurity=true` 时的 `https://h5.m.taobao.com` 变为空。因此单独切换 `webSecurity` 没有解决问题，后续必须继续由成功环境逐项对照，详见 `docs/淘宝搜同款当前诊断摘要.md`。

## 4. 当前修改方案

### 搜索会话

- 固定使用一个全新的持久分区：`persist:dianxiaoer-taobao-same-search-v1`。
- 所有采购账号共享这一台“淘宝同款专用浏览器”，采购账号切换不会切换搜索账号。
- 第一次点击搜索且专用分区未登录时，打开淘宝登录页，并带固定搜索承载页作为回跳地址。
- 用户手工登录；登录 Cookie、页面、MTOP Token 和身份环境稳定后，窗口自动隐藏并长期复用。
- 专用搜索分区绝不读取、复制、注入或清理采购账号 Cookie/站点存储。
- 保留会话身份指纹、代际校验、请求前复核和登录/验证检测。

### 采购流程隔离

- 搜索结果只是由专用账号取得。
- 点击结果后打开商品页，仍明确使用当前选择的采购账号分区：`persist:purchase-{accountId}`。
- 商品页登录、SKU 自动选择、货源绑定/取消、价格提取、改地址和下单逻辑都不得切换到专用搜索分区。
- `injectTaobaoCookiesFromAccount()` 仍保留，但只允许作为采购商品页原有兜底使用，搜索窗口不得调用。

## 6. 关键修改内容

1. `getTaobaoSamePartition()` 不再接受采购账号决定分区，固定返回专用 partition。
2. `getOrCreateTaobaoSearchWindow(accountId)` 只创建/复用一个搜索窗口，不再从 `persist:purchase-*` 或服务端加载 Cookie。
3. 新增专用登录入口；缺少登录 Cookie 时直接显示窗口并返回 `needLogin`，不得进入图片准备和接口请求。
4. 登录完成后跳到固定承载页，等待登录 Cookie、MTOP Token、页面加载和身份代际稳定，再隐藏窗口。
5. `searchTaobaoImageDirect()` 在发送请求前再次检查专用会话登录状态和身份一致性。
6. `openTaobaoSameProductPage()` 仍通过 `getTaobaoPurchasePartition(accountId)` 打开采购商品页。
7. 已撤销失败的“按采购账号创建搜索分区、复制 Cookie、排除/恢复 MTOP Token、清空搜索 storage”的临时实现。

## 7. 当前待解决事项

1. 已将“开始搜同款”日志移动到登录和环境检查通过之后；首次点击只记录“收到搜同款请求”，人工日志已验证登录前不会准备图片或发送 MTOP。

3. 淘宝返回 `RGV587` 且无验证 URL 时最多保留唯一一次受控重试；重试决策不依赖 Bixi 是否存在，不允许刷新循环或无限重试。
4. 成功一次后验证第二件、第三件商品是否真正走 `WARM_REUSE`，耗时是否显著下降。

## 8. 风险点

- 淘宝对高频请求、环境突变、无完整安全参数、重复刷新和登录态切换敏感，错误试验可能导致专用账号暂时受限。
- 不能把淘宝返回“被挤爆”简单等同于服务器繁忙；结合本项目日志，它经常是风险环境响应。
- Cookie 出现不等于登录流程完成。必须同时确认页面不在登录/验证 frame、MTOP Token 存在、页面加载完成、身份代际稳定。
- 不能因为搜索账号独立，就让商品页也使用搜索账号；这会破坏采购账号、购物车、地址和订单归属。
- 不要清理 `persist:purchase-*`，也不要在搜索初始化时调用采购 Cookie 恢复函数。
- 不要使用自动刷新循环修复价格圆点或搜索失败，历史上曾造成页面跳动、白屏和淘宝登录退出。
- 本轮是 Electron 主进程变更；未来如果发布，必须走全量发布，不能只做 renderer 热更新。
