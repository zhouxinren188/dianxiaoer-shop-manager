## 2. 问题与需求背景

淘宝按图搜同款已经具备请求 MTOP、展示结果、打开商品页、选择 SKU 和绑定货源等能力，但维护过程中暴露了以下问题：

1. 专用账号登录后第一次真实请求长期出现 `RGV587` 或 `FAIL_SYS_USER_VALIDATE`。
2. 登录窗口曾与搜索承载窗口共用同一个 BrowserWindow，登录回跳可能被搜索承载页导航提前打断。
3. 旧实验曾复制或恢复采购 Cookie，既不能恢复完整淘宝设备环境，又可能影响采购账号登录、购物车、优惠价和下单。
4. 网络或页面 frame 异常时，IPC Promise 可能长期不返回，前端一直显示“正在调用淘宝图搜服务”。
5. 淘宝会间歇返回 `SUCCESS` 但商品数组为空，单次请求不足以稳定得到结果。
6. 完成滑块后，旧的30分钟本地风险冷却没有及时解除，造成“验证已通过但再次搜索仍失败”的假象。
7. 搜同款结果历史原来只保存100条；需求调整为保存30天、最多10000条并滚动淘汰最早数据。
8. 正式版 1.9.53 首次读取 IndexedDB 缓存时可能永久 pending，界面只显示“暂无同款商品”，实时搜索 IPC 根本没有进入主进程。

## 3. 原因分析与已确认结论

### 3.1 登录回跳竞争是主要时序缺陷

旧代码在 `did-navigate` 发现页面离开登录/验证地址后，可能立即对同一个窗口执行 `loadURL()`，强制切到图搜承载页。淘宝登录回跳仍可能在写入 Cookie、LocalStorage、IndexedDB、设备状态或完成自动登录确认，因此提前导航会得到“不完整的新设备登录环境”。

### 3.2 Bixi 缺失不是已证实根因

已知成功对照资料：

- `C:\Users\Administrator\Desktop\蚂蚁工具箱淘宝同款成功调用诊断.txt`
- `docs/蚂蚁工具箱淘宝同款成功调用关键对照.md`

蚂蚁工具箱成功样本中 `bx-ua`、`bx-umidtoken`、`bx_et` 三项同样不存在，第一次 MTOP 仍在约484ms内返回原始60条。因此：

- `bixi.coherent=false` 只能作为诊断现象，不能认定为失败原因。
- 禁止伪造、写死或跨会话复制 Bixi。
- 每次请求只从当前页面读取当前值；缺失时允许按真实环境发送。

### 3.3 `webSecurity=false` 在当前 Electron 版本会制造异常网络特征

Electron 41 / Chrome 146 实测：关闭 `webSecurity` 后，真实出站 `Origin` 从 `https://h5.m.taobao.com` 变为空，而且仍返回相同 RGV587。因此当前固定使用 `webSecurity=true`，不照搬 Electron 35 成功工具的配置，也不降级或伪造 UA。

### 3.4 登录前没有真正偷跑 MTOP

早期“开始搜同款”日志位置过早，造成登录前已请求的错觉。真实日志证明登录前会在 Cookie 检查处返回，没有图片准备和 `request attempt=1`。现在已把“IPC已进入主进程”、窗口初始化、承载页稳定、图片准备和真实请求分阶段记录。

### 3.5 永久转圈来自未设上限的异步等待

`loadURL()`、损坏/导航中的 frame `executeJavaScript()`、会话初始化和开发热重载中断都可能让 IPC 长时间不完成。只给网络请求设置超时不足以覆盖首次窗口创建和页面检查。

### 3.6 SUCCESS 零商品是接口正常响应的一种结果

真实日志多次出现第一次 `SUCCESS` 为0条，随后同环境第二次返回20条；也出现过连续5次均为0条。因此零商品不能按 RGV、Token、HTTP 错误处理，必须在同一任务和环境内快速补查。

### 3.7 原历史存储不适合10000条

旧历史使用 `localStorage` 保存完整结果，逻辑上即使把上限改成10000，也可能提前触发浏览器容量限制。当前改为 IndexedDB 优先，并迁移旧 `localStorage` 数据；无 IndexedDB 时才降级使用原存储。

### 3.8 IndexedDB 通用请求封装曾导致成功回调永久悬空

旧 `requestResult()` 在每个请求成功时都把 `request.result` 当作 `IDBDatabase`，设置 `onversionchange` 并调用其 `close()`。这只适用于 `indexedDB.open()`：`store.get()` 未命中返回 `undefined`，`store.count()` 返回 number；在成功回调中访问或设置属性会抛错，但 Promise 没有 resolve/reject，所以外层 `try/catch` 无法捕获并永久等待。`OrderList.vue` 又在设置 loading 和调用实时 IPC 之前等待历史读取，因此形成“暂无同款商品”、无主进程日志、无 v2 会话目录的精确症状。

## 4. 修改方案与关键实现

### 4.1 专用搜索会话与采购会话彻底隔离

- `getTaobaoSamePartition()` 固定返回 `persist:dianxiaoer-taobao-same-search-v2`。
- 搜索只使用该 partition 的原生 BrowserSession，不从采购账号或服务端加载 Cookie。
- 所有采购账号共享一个专用搜索账号和长期搜索窗口，采购账号切换不会冷启动搜索账号。
- `openTaobaoSameProductPage()` 仍使用 `getTaobaoPurchasePartition(accountId)`；采购 Cookie 兜底函数只允许在商品页路径调用。

### 4.2 登录窗口与搜索承载窗口分离

- 登录 BrowserWindow：只负责登录、滑块、安全验证和完整回跳。
- 搜索 BrowserWindow：隐藏、长期保留，只负责固定承载页和页面内 XHR。
- 两个窗口共用同一固定 v2 partition 和 BrowserSession，但不复制 Cookie。
- 登录窗口导航事件只记录时间和 URL，绝不在回调中调用 `loadURL()`。
- 回跳离开登录/验证页后先隐藏登录窗口；如果又进入登录或验证页则重新显示。
- 只有全部 frame 不在登录/验证页、主页面 complete、不再 loading、登录 Cookie 指纹和 `_m_h5_tk` 稳定，且导航与身份变化静默至少2秒后，才关闭登录窗口并创建/确认搜索承载窗口。

### 4.3 严格承载页与身份稳定检查

- `bootstrapComplete` 必须同时满足：
  - URL 是固定图搜承载页；
  - 主页面 `readyState=complete`；
  - 页面不再 loading；
  - `_m_h5_tk` 存在；
  - 导航和身份变化稳定。
- 关键身份 Cookie 使用不可逆指纹和会话代际监控。
- 每次发 MTOP 前再次比对身份代际和指纹；变化时停止请求，不热复用旧环境。

### 4.4 SUCCESS 零商品高频补查

- 仅当 MTOP 返回 `SUCCESS/调用成功` 且原始或过滤后商品数为0时触发。
- 单个搜索任务总请求上限5次，间隔固定200ms。
- 5次必须串行使用同一 BrowserWindow、webContents、session 和 partition。
- 每次重新读取当前 `_m_h5_tk` 和页面 Bixi，并重新生成时间戳和 sign。
- 图片 base64 和搜索参数保持不变；任意一次得到有效商品立即停止。
- 第5次仍为空才提示“接口调用成功，但未返回同款商品”。
- RGV587、`FAIL_SYS_USER_VALIDATE`、Token失效和HTTP异常进入各自分支，不计作零商品补查。
- 同一 partition 的不同搜索任务通过队列串行，禁止并发五次补查。

### 4.5 风控、验证与冷却

- 验证地址始终在独立登录窗口打开，不把搜索承载窗口改载到验证页。
- 验证回跳、账号环境和搜索承载页均稳定后立即清除本次本地风险冷却。
- 未完成验证，或淘宝只返回无验证地址的风控时，仍保留受控冷却和错误提示。
- 不通过刷新、重建 partition、重新登录或复制 Cookie 绕过风控。

### 4.6 转圈与异步超时保护

- 主进程 `loadURL()` 等待上限：8秒；之后转入严格页面状态检查，不盲目刷新。
- 单个 frame 页面脚本读取上限：750ms；全部 frame 总读取上限：1.5秒。
- 先扫描全部 frame URL，再执行页面脚本，避免损坏主 frame 阻塞登录 iframe 识别。
- 专用会话首次 Cookie 读取上限：3秒。
- renderer 等待搜同款 IPC 上限：60秒；超时后必定解除 loading 并提示重新搜索。

### 4.7 脱敏网络诊断

日志只记录：

- 实际 Cookie 头中的 Cookie 名称，不记录值；
- `_m_h5_tk`、`_m_h5_tk_enc`、`cookie2`、`unb`、`cookie17` 是否实际发送；
- CDP `associatedCookies` 的名称和阻止原因；
- 请求头名称、Origin、去查询参数后的 Referer、Sec-Fetch、Client Hints；
- Token/Bixi 只记录存在性、长度或不可逆指纹。

### 4.8 搜同款历史记录

- 有效期：30天。
- 上限：10000条搜索记录。
- 每条最多保存20个商品结果。
- 键由“当前用户 + 采购账号 + 销售 SKU + 去查询参数的主图 URL”组成。
- 使用 IndexedDB 保存大容量结果，并自动迁移旧 `localStorage` 数据。
- 每次读取或保存都会清除超过30天的数据；没有后台定时清理任务。
- 新记录写入后若超过10000条，按 `cachedAt` 删除最早记录。
- 同一个键重新搜索会更新结果和时间，不额外增加一条。
- IndexedDB 不可用或异常时缓存读取按未命中处理，不阻止真实淘宝搜索；保存失败也不影响本次结果展示。
- 通用 IndexedDB 请求只 resolve 原始 `request.result`；仅在 `indexedDB.open()` 成功取得真实数据库连接后设置 `onversionchange`。
- 历史读取上限为1.5秒；请求异常或永久 pending 均按缓存未命中处理，继续实时搜索。
- 主进程另有图片准备内存缓存：20分钟、最多20张，进程退出即清空；它与30天搜索结果历史不是同一缓存。

### 4.9 商品页价格手动刷新

- 商品详情窗口没有自动 `reload()`；只在初次打开时执行一次 `loadURL()`。
- 旧的 `price-recovery-reload` / `scheduleSkuPriceRecovery` 自动价格恢复逻辑已经移除，测试禁止重新引入。
- 商品页在“绑定货源/取消绑定”浮窗左侧8px处增加“刷新页面”浮窗；只有用户点击时才调用一次 `window.location.reload()`。
- 页面刷新会销毁当前 document；主进程保留 `dom-ready`、`did-finish-load`、`did-navigate` 的重注入监听，使刷新与货源控件在新 DOM 中恢复。
- 刷新始终发生在当前商品窗口和 `persist:purchase-{accountId}` 分区，不读取、复制或清理采购 Cookie。

## 7. 可能风险与尚未覆盖范围

1. 淘宝外部风控不可由本地代码完全消除。相同环境也可能返回零商品、RGV587或滑块，不能把所有失败都视为本地缺陷。
2. 5次/200ms补查只允许用于 SUCCESS 零商品；扩大重试范围可能触发更强风控。
3. v2 是长期持久会话。随意升级 partition 名、清理站点数据或重建窗口会丢失已验证环境。
4. renderer 的60秒超时用于解除界面等待，不等同于强制取消主进程任务；主进程仍通过队列和自身超时收尾。
5. IndexedDB 记录属于当前 renderer origin 和应用用户数据。清理应用用户数据、改变 renderer origin 或删除数据库会丢失历史；历史不上传服务端，也不跨设备同步。
6. IndexedDB 不可用时会降级到 localStorage，降级模式可能在达到10000条前先碰到浏览器容量限制，但不会影响实时搜索结果。
7. 本轮没有执行真实采购下单、支付或改地址操作，避免对真实业务数据产生外部副作用；合并前仍建议主线做一轮采购流程回归。
8. IndexedDB 悬空修复本身没有修改主进程；但当前待发布批次新增了商品页手动刷新浮窗并修改 `src/main/taobao-same-search.js`，因此必须全量发布，不能只发布 renderer 热更新。

## 8. 后续维护注意事项

1. 每次先按时间线看日志：`IPC已进入主进程` → 窗口/会话初始化 → 承载页稳定 → 图片准备 → `request attempt` → response。不要只看“开始搜同款”。
2. 不要把 `bixi.coherent=false` 当成失败根因，也不要伪造或跨会话复用 Bixi。
3. 不要在 `did-navigate` 等导航回调中执行 `loadURL()`；登录窗口只记录状态。
4. 不要复制或清理采购 Cookie。搜索和商品页必须分别保持专用 v2 与 `persist:purchase-{accountId}`。
5. 新增重试必须证明不会跨窗口、webContents、session、partition，也必须经过同 partition 队列。
6. 新增诊断只能记录名称、布尔值、长度、结构和不可逆指纹，禁止记录 Cookie、Token、手机号或完整敏感 URL。
7. 修改历史数据库结构时必须提升 `TAOBAO_SAME_HISTORY_DB_VERSION`，在 `onupgradeneeded` 中兼容升级，并保留 `onversionchange` 主动关闭旧连接。
8. 30天历史清理是“读取或保存时懒清理”，不是后台定时器；不要误认为到点立即触发任务。
9. 同一历史键重新搜索应覆盖旧记录并刷新 `cachedAt`；第10001个不同键才淘汰最早记录。
10. 修改后至少运行两个专项测试、全量测试、构建和 `git diff --check`；涉及存储时增加能打印断言、设置 watchdog、成功时自然退出的真实 Electron IndexedDB 验证，不能把人工终止的进程算作通过。
11. `npm start` 报5174占用时，先确认是否已有同一支线实例，禁止误杀主线5173/3002进程。
12. 提交前按当前差异逐文件核对并只暂存搜同款相关文件；不要提交 `.dev-user-data-*`、`out`、临时验证脚本或用户原有脏文件，不要再机械套用旧提交的“7个文件”数量。
13. 用户要求提交时，提交成功后主动报告 commit hash、测试结果和发布类型；当前批次因包含商品页主进程注入代码，必须明确说明需要全量包。

1. 完整阅读本说明。
2. 阅读 `docs/淘宝搜同款当前诊断摘要.md` 和蚂蚁工具箱成功对照。
