# 采购物流时效学习与货源推荐维护说明

## 1. 背景与目标

采购下单可能配置多个淘宝/天猫货源。仅比较售价无法判断实际到货速度，而单个货源、单个商家的历史采购次数通常太少，按商家单独建模容易被偶然样本误导。

本功能使用所有用户已经产生的真实采购物流记录，学习：

- 不同发货地区在不同下单时段进入快递物流网络的速度；
- 发货地到当前收货地的实际运输时效；
- 单个货源在样本充分时的发货表现和未发货风险；
- 多货源之间的最低价格、最优时效和采购优选结果。

当前只展示“预计 1-2 天”这类区间，不展示具体到达日期。快递100等外部预计到达接口尚未接入。

## 2. 原因分析

旧方案主要依赖固定地区时效配置和默认 24 小时发货准备时间，存在以下问题：

1. 同一地区上午下单和接近傍晚下单的当天交件概率不同；
2. 单个商家样本稀疏，无法稳定学习商家截单时间；
3. 物流轨迹有时缺少明确“揽收”节点，只有“已发往/运输中”；
4. 快递轨迹中的批量扫描时间不一定等于真实车辆发车时间，但能证明包裹何时进入物流网络；
5. 按周末拆分样本不符合电商实际经营规律，并会进一步稀释样本，因此当前不区分工作日和周末。

## 3. 整体链路

```text
采购订单物流同步/历史回填
        ↓
解析下单、首次进入物流、签收时间和起终点行政区
        ↓
shipping_timeliness_observations 结构化样本表
        ↓
采购弹窗请求 /api/shipping-timeliness/recommend
        ↓
地区时段交件 P50/P80 + 路线运输 P50/P80
        ↓
预计天数、价格最低、最优时效、采购优选
```

推荐时不会重新解析采购订单中的物流原文，而是读取已经结构化的近 90 天样本。历史回填会在服务启动后执行，并每 6 小时补扫一次近 180 天尚未生成有效样本的采购单。

## 4. 样本定义

每个有效样本保存：

- 采购订单编号、平台、货源键；
- 发货省/市/区县；
- 收货省/市/区县；
- 下单时间 `ordered_at`；
- 首次进入物流网络时间 `picked_up_at`；
- 签收时间 `signed_at`；
- 下单到进入物流的交件耗时 `dispatch_hours`；
- 进入物流到签收的运输耗时 `transit_hours`；
- 下单到签收总耗时 `total_hours`；
- 正常签收或未发货风险结果 `outcome`。

为兼容现有数据库，字段仍叫 `picked_up_at`，实际语义已经统一为“首次有效进入快递物流网络时间”。优先使用明确揽收节点；缺少揽收时，使用首个有效的“已发往/运输中”节点。

以下节点不能作为进入物流：仓库已接单、打印完成、商品已经下单、正在打包、等待揽收。拒收、退回、返件等异常轨迹不进入正常签收时效样本。

样本表只保存行政区和时间，不保存收件人、手机号、完整收货地址或物流原文。

## 5. 计算规则

### 5.1 发货准备时间

当前下单时间按每 2 小时一个区间匹配历史样本，例如 12:00-14:00。电商日常不区分工作日和周末。

按以下顺序降级：

1. 单个货源相近下单时段至少 5 个已签收样本；
2. 发货城市 + 2 小时时段至少 5 个样本；
3. 发货省份 + 2 小时时段至少 10 个样本；
4. 发货大区 + 2 小时时段至少 20 个样本；
5. 样本仍不足时使用服务器默认 24 小时。

同时统计“下单当天进入物流网络”的订单数量和比例。该比例用于诊断；预计耗时不再额外叠加概率，因为交件 P80 已包含当天和次日进入物流的真实分布。

### 5.2 路线运输时间

路线运输时效按以下顺序降级：

1. 发货城市 → 收货城市至少 3 个样本；
2. 发货省份 → 收货省份至少 5 个样本；
3. 样本不足时使用服务器地区默认区间。

### 5.3 预计区间

```text
保守预计耗时 = 交件 P80 + 路线运输 P80
区间下限参考 = 交件 P50 + 路线运输 P50
```

界面将小时数转换为“预计 1-2 天”等范围。P50 表示一半样本不超过该耗时；P80 表示 80% 样本不超过该耗时。

### 5.4 发货风险

平台同步确认后超过 72 小时仍没有任何有效物流网络节点，才记录未发货风险。已有“已发往/运输中”节点但缺少明确揽收节点时，不会误判未发货。

单货源在相近下单时段至少 5 个结果样本、且超时未发或未发失败比例达到 30% 时，标记高风险并取消时效推荐资格。

### 5.5 推荐标签

- `价格最低`：多个有效价格中最低的货源，允许并列；
- `最优时效`：非高风险货源中预计分数最低的货源，允许并列；
- `采购优选`：同时命中价格最低和最优时效，只显示采购优选，不重复显示另外两个标签。

## 7. 查询与性能

推荐接口最多比较 30 个货源。数据库查询只读取：

- 近 90 天样本；
- 相关发货大区；
- 当前 2 小时时段；
- 当前货源键对应的风险样本。

查询不会扫描和解析原始物流文本，但目前仍会从结构化样本表取出匹配行后实时计算百分位。当前数据规模可用；样本达到几十万且并发明显增加后，应增加 30-60 分钟结果缓存或地区/路线汇总表。

## 8. 已知风险和限制

1. 大促、极端天气、春节等特殊日期尚未单独建模；P80能降低少量异常值影响，但不能识别事件原因；
2. 物流平台扫描时间不等于真实揽收或车辆发车时间，本功能只将其解释为“已进入物流网络”；
3. 发货地来自物流首个有效地区，缺失时才回退货源链接保存的发货地；
4. 路线学习当前以城市路线为主、样本不足降级到省份，不直接为每个区县建立独立模型；
5. 当前没有外部冷启动数据；无真实样本时仍依赖默认地区配置；
6. 推荐结果由全体用户的行政区级匿名样本汇总产生，不按单个用户隔离；
7. 修改样本阈值、时间桶或 `picked_up_at` 语义时，必须同步更新测试和本说明。

## 9. 测试方法

```powershell
npx.cmd vitest run tests/shipping-timeliness.test.js
npm.cmd test
npm.cmd run build
git diff --check
```

专项测试覆盖：

- 物流年份纠正和跨年解析；
- 揽收、首个有效发往节点和签收识别；
- 拒收/退回过滤；
- 城市、省份、大区和默认值分级回退；
- 2 小时时段匹配且不区分工作日/周末；
- 当天进入物流比例、P50/P80；
- 单货源修正和未发货风险；
- 已进入物流但缺少揽收时不误判未发货；
- 历史物流反推发货地；
- 数据库查询范围和参数；
- 价格相同时效推荐与风险排除。

## 10. 后续维护建议

1. 部署顺序应为数据库/业务服务端先部署，接口验证通过后再发布 renderer；
2. 服务端部署后确认 `shipping_timeliness_observations` 表、索引和历史回填日志正常；
3. 观察诊断日志中的 `dispatchBasis`、`basis`、`sampleCount`、`routeP80Hours` 和 `regionalDispatchPerformance`，不要只看最终天数；
4. 如接入快递100，将外部结果保存为独立“冷启动基准”，优先级必须低于真实历史样本，禁止伪装成真实订单样本；
5. 快递100按发货城市、固定沭阳收货地和白天三个代表时间请求，必须缓存，密钥只能放服务端；
6. 数据量增长后优先增加结果缓存，再考虑定时汇总表；
7. 大促建模应采用特殊日期标签或近期异常修正，不恢复简单的工作日/周末拆分。
